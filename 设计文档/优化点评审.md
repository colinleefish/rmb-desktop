# 优化点评审

> 本文档整理自一次架构评审讨论，用于记录项目当前存在的可优化点。
> 评审对象：`internal/worker/` 下的记忆凝练 pipeline（L1 extract / L2 scene / L3 memory / embed）+ 召回与数据库相关实现。

## 背景：凝练成记忆的 pipeline 概览

平台三步：**捕获（ingest）→ 记忆（distill）→ 召回（recall）**。凝练成记忆由 `internal/worker/runner.go` 启动 4 个并行 worker：

| Worker | 名称 | 轮询间隔（默认） | 职责 |
|---|---|---|---|
| L1 | extract | 15s | 对话 → 原子事实（atoms） |
| L2 | scene | 15s | 原子 → 场景摘要（scenes） |
| L3 | memory | 5min | 原子跨会话汇总 → 记忆（memories） |
| embed | 向量化 | 30s | 给 atoms/scenes/memories/skills 补 embedding（可选） |

触发方式是「轮询 + 状态机」而非事件驱动：`session.Upload` 写入 `session_turns` 并更新 `pipeline_state`（每 session 一行，状态 `idle/pending/running/failed`），逐级向后推进。L3 不是按 session 处理，而是全局 rollup，按 `slug` 跨会话分组后蒸馏出记忆（版本化）。

---

## 🔴 高优先级：真的会出问题

### 1. SQLite 并发写没有配置，大概率会撞 `database is locked`

`internal/db/db.go` 里 DSN 只设置了两个 pragma：

```go
dsn := path + "?_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)"
```

**没有 `_busy_timeout`，也没有 `SetMaxOpenConns(1)`**。全局 grep 过，整个 `internal/` 和 `cmd/` 里都没有这两个词。

问题在于：WAL 模式允许多读单写，但 mattn/go-sqlite3 默认 `busy_timeout=0`，**写锁冲突时立刻返回 `SQLITE_BUSY`**，不会等待。而 worker 们恰恰是并发写的：

- L1 `RunParallel` 最多 **8 个 goroutine 并发**，每个 `processSession` 都要 `BeginTx` → 写 → commit（`prepareBatch` 一次、`persistBatch` 又一次）
- L2 最多 4 个并发写
- embed worker 每 30s 批量写
- HTTP server 的 `session.Upload` 也在写

这几路一起跑，写锁竞争是常态。数据量小、并发低时可能没触发，但一旦 L1 并发爬上去或导入会话，**会随机报 `database is locked`，且现有错误处理会把 transient 判断成 failed，造成 LLM 调用重试浪费**。

**建议**：加 `_busy_timeout=5000`（或 `SetMaxOpenConns(1)` 串行化所有 DB 访问，对 SQLite 单机最省心）。强烈建议优先修。

### 2. 向量召回是 Go 里的暴力线性扫描，没用到 sqlite-vec 的 KNN

`internal/recall/vector.go` 里：

```go
SELECT uri, ..., embedding FROM memories WHERE superseded_at IS NULL AND embedding IS NOT NULL
```

这条 SQL **把全表所有向量都捞进内存**，然后 `rankVectors` 在 Go 里对每一条做 `cosineSimilarity` 再排序取 top-k。`init()` 里虽然调了 `sqlite_vec.Auto()` 注册了扩展，但**检索路径从未用过 vec 虚拟表的 KNN 查询**。

也就是说 sqlite-vec 现在只被当成「向量的序列化/反序列化工具」，检索是完全的 O(N) 暴力扫描。记忆上千条之后，每次召回都要全量算一遍余弦。这和「用 sqlite-vec」的初衷脱节——要么真的用 `vec_virtual` 表 + `MATCH` 做 ANN，要么就别引入这个 CGO 依赖。

### 3. 永久性失败没有重试上限，会无限烧 token

L1/L2 的 `handleProcessError` 里，非 transient 错误把状态置为 `failed`。但下一轮 `selectCandidateSessions` **依然会捞 `failed` 的 session**（L1 按 `l1_extracted_at IS NULL`，L2 按 `l2_status IN ('pending','failed')`）。

结果就是：如果某个 session 的数据让 LLM 每次都返回非法 category、或解析一直失败，这个 session 会**每 15 秒被重试一次，永不停歇**。没有 max-retry、没有 backoff、没有死信队列。这是实打实的 API 费用隐患，也是正确性隐患（错误日志会被刷屏）。

**建议**：加一个 `failed_count` 或 `failed_at`，超过阈值就跳过或人工介入。

## 🟡 中优先级：会随数据量/时间退化

### 4. L3 每次 rollup 全表扫描，且任何 session 变更都会触发全量检查

`memory/worker.go` 的 `rollup` 每 5 分钟一次，每次都 `loadAllAtoms`（`SELECT ... FROM atoms` 全表）+ `loadAllScenes` 全表。没有水位线、没有增量标记。老用户跑几个月后 atoms 可能几万条，全局 rollup 会越来越慢。

而且 `correction.ForTargets` 的查询也是 `SELECT ... FROM corrections WHERE retracted_at IS NULL` **全表捞，再在 Go 里按 wanted 过滤**——其实 `wanted` 已经算好了，SQL 里完全可以用 `json_each` 过滤，却没用。

### 5. `EnqueueSessionsForMemoryTargets` 的 join 不可走索引

```sql
JOIN scenes sc ON ('rmb://scenes/' || lower(sc.id)) = je.value
```

字符串拼接 join，非 sargable。数据量大时慢，而且逻辑绕（memory → source_scene_uris → scene → session），可读性也差。

## 🟢 低优先级：设计上可以更干净

### 6. `pipeline_state.l3_status` 是个「脏标记」，概念上有点拧巴

L3 是全局作业，不是按 session 的。`l3_status` 其实只承担「这个 session 的 atoms 变了，需要重新蒸馏」的作用。可以改成一个单独的 `dirty` 布尔或 `l3_dirty_at`，语义更清晰，也不容易和 L1/L2 的状态机混淆。

### 7. 同名字场景的 ID 稳定性依赖 LLM 返回顺序

`sceneIDForName(sessionID, displayName, dup)` 里的 `dup` 是按 LLM 返回顺序递增的（`dupCount[s.DisplayName]++`）。如果某次 LLM 把两个同名场景的返回顺序对调（LLM 输出本来就不稳定），它们的确定性 ID 会互换 → `ON CONFLICT` 更新到错误的行 → 场景内容错位、embedding 作废重算、source 引用错乱。当 display_name 唯一时没问题，但 prompt 没有强制 display_name 唯一，所以这是真实的隐患。

### 8. `mergeTurnMessages` 按字节截断，可能切坏 UTF-8

`out.WriteString(next[:remaining])` 是字节切片，24000 字符的截断边界如果落在多字节 UTF-8 中间，会往 LLM 里送非法字符。大概率无伤大雅（LLM 能容错），但属于不严谨。

### 9. `distillDelay = 1s` 是粗糙的限速

L3 每个 bucket 之间睡 1 秒，而且是**持 GlobalLock 的状态下睡**。bucket 一多，一次 rollup 会长时间占住全局锁，期间任何新 session 的 L3 蒸馏都排不上。可以换成基于 LLM 端 rate limit 的 token 预算，或至少把锁粒度拆开。

---

## ✅ 值得肯定的地方（这些是真的好）

- **幂等性做对了**：L3 的 `bucketUnchanged` 用 provenance（来源场景 + 修正 URI 集合）判断是否重蒸馏，避免每次全量重烧 LLM；memories 版本化 + active 唯一索引是干净的事实演化模型。
- **崩溃自愈**：`recoverPipelineState` 把 `running` 重置为 `pending`，桌面应用被强杀后能恢复。
- **成本护栏**：AIMD backpressure 在 429 时并发减半、积压时爬升，方向对，实现也简洁。
- **ingest-only 降级**：没配 key 时优雅退化为只摄入，符合「本地优先」产品哲学。
- **correction 优先级最高**：人工修正作为 ground truth 覆盖所有事实，且 retract 后能触发重蒸馏，闭环完整。

---

## 整体判断与建议动工顺序

这是一份「个人开发者 + 早期产品」里相当优秀的架构——分层清晰、状态机完整、幂等和自愈都有考虑。但它有一个典型的个人项目特征：**写的时候脑子里是「小数据、低并发」，所以 SQLite 并发、向量检索、全表扫描这些地方都用了最省事的写法**。

建议按以下顺序动手：

1. **先修 SQLite 并发**（加 `_busy_timeout` 或串行化连接）——稳定性问题，会直接导致丢记忆/重试；
2. **加失败重试上限**——成本问题；
3. 之后才是 L3 增量化、向量检索换成真 KNN 这类「规模问题」。
